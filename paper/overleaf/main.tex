\title{CSE-Tutor: Verified Synthetic Data for Fine-Tuning a 1.5B-Parameter Tutor Model for Computer Science Education}

\author{\IEEEauthorblockN{Satya Dedeepya}
\IEEEauthorblockA{Course project, Deep Learning\\
\url{github.com/satyadedeepya/slm_dl_project}}}

\maketitle

\begin{abstract}
Small language models can run on a student's laptop, but they are unreliable on the numerical problems that dominate computer-science examinations. We fine-tune Qwen2.5-1.5B-Instruct with LoRA as a tutor for six subjects (data structures and algorithms, programming, databases, operating systems, computer networks and deep learning) using a mixed instruction set whose distinctive component is \emph{programmatically verified} data: 3,000 problems whose step-by-step solutions and answers are computed by executing the underlying algorithm. All training and evaluation runs on an integrated Intel Arc GPU. On held-out test sets, fine-tuning significantly improves text-to-SQL execution accuracy (50.5\ra 60.0), functional-dependency problems (15\ra 30) and network numericals (1\ra 8) over the base model (exact McNemar $p<0.05$), without loss on code generation. An ablation that removes only the verified data eliminates these numerical gains. A continued-training stage adds deep learning, which raises value-level accuracy on held-out deep-learning numericals from 15.8\% to 26.0\% (paired permutation $p=0.013$) while every earlier gain is retained. Two further stages train on teaching-style answers; judged blind against the base model on 39 held-out questions, the final model wins the numerical problems 13--5 (p = 0.096) while the base model still explains open concept questions slightly better (6--11--3, not significant). Error analysis shows that the remaining failures are mostly procedural: the model reproduces the solution template but executes multi-step algorithms unreliably.
\end{abstract}

\begin{IEEEkeywords}
small language models, LoRA, synthetic data, data verification, computer science education, text-to-SQL

\section{Introduction}
Students preparing for university examinations, GATE and placement interviews need an assistant that explains concepts, solves numerical problems step by step and writes correct code and SQL. Large hosted models do this well but cost money and need connectivity; a 1.5B-parameter model runs locally, but out of the box it computes CPU-scheduling waiting times, page faults and subnet ranges incorrectly because it pattern-matches instead of executing the procedure.

The common recipe for adapting a small model is to fine-tune on question--answer pairs written by a larger model~\cite{selfinstruct,glan}. Such labels are unverified, and a small student model can learn the teacher's mistakes. We take a different route for the part of the curriculum that is algorithmic: we write generators that sample random problem instances and \emph{compute} their solutions by running the algorithm, so every label is correct by construction. We then ask three questions:
\begin{itemize}
\item \textbf{RQ1:} how much does LoRA fine-tuning improve a 1.5B model on CS tasks compared with zero- and few-shot prompting?
\item \textbf{RQ2:} does the verified numerical data cause the improvement on numerical problems, or does the rest of the mix?
\item \textbf{RQ3:} can a new subject (deep learning) be added cheaply by continued training without forgetting earlier skills?
\item \textbf{RQ4:} does the fine-tuned tutor \emph{explain} better than the base model, not only answer more accurately?
\end{itemize}
Our contributions are (1) verified generators for 41 problem types across operating systems, networks, databases and deep learning, with tests against textbook examples and PyTorch; (2) a controlled ablation isolating the effect of verified data; (3) a statistically careful evaluation (bootstrap confidence intervals, exact McNemar tests, separated format failures) on seven held-out benchmarks; (4) an error taxonomy of the fine-tuned model; (5) an explanation-style training stage judged blind against the base model; and (6) a local chat interface. The whole pipeline runs on a laptop with an integrated GPU.

\section{Related Work}
\emph{Parameter-efficient fine-tuning.} LoRA~\cite{lora} trains low-rank updates of frozen weights; QLoRA~\cite{qlora} adds 4-bit quantisation of the base model. We use LoRA on all attention and MLP projections of Qwen2.5-1.5B-Instruct~\cite{qwen25,qwencoder}.

\emph{Models for CS education.} GuideLM~\cite{guidelm} shows that small supervised sets can shape pedagogical behaviour; QLoRA has been applied to DSA problems~\cite{dsaqlora}; local open-source teaching assistants are studied in~\cite{aita,smallmodels,vta}. CS-Bench~\cite{csbench} is the closest benchmark and serves as our multiple-choice evaluation.

\emph{Synthetic instruction data.} Self-Instruct~\cite{selfinstruct} and GLAN~\cite{glan} generate instruction data with language models. Our generators are programs, so correctness does not depend on a teacher model; LLM-written data in our mix is filtered by answer-key agreement instead.

\emph{Forgetting.} Parameter-efficient tuning still forgets~\cite{forgetting}; we therefore keep replay data and measure code generation and examination questions after every stage.

\section{Data}
\subsection{Verified generators}
Each generator samples parameters, runs the algorithm and writes a solution in a fixed teaching format that ends with a \texttt{Final answer:} line, plus a machine-readable grading specification (Table~\ref{tab:gen}). Questions state their conventions (tie-breaking, whether C-SCAN counts the return seek) so the reference answer is unambiguous. Test problems are drawn from parameter pools disjoint from training. Correctness is checked by unit tests against textbook worked examples (e.g.\ Silberschatz scheduling and page-replacement figures), property tests (Belady's optimality, safety-sequence validity), and, for deep learning, by recomputing answers with PyTorch layers and autograd.

\subsection{The full training mix}
The first-stage mix (9,335 examples, 2.68M tokens; Table~\ref{tab:mix}) combines the generators with GATE/ISRO previous-year questions whose explanations were produced by a teacher model \emph{without the key} and kept only when the teacher agreed with the official answer (990 of 1,154), concept Q\&A over a 133-topic syllabus, Q\&A grounded in four openly licensed textbooks, Spider~\cite{spider} text-to-SQL with real schemas, MBPP~\cite{mbpp} and CodeAlpaca for code, and general replay data. All sources are deduplicated with MinHash and decontaminated against every evaluation set with 13-gram overlap. GATE papers up to 2020 and half of 2021--2026 are used for training; the other half of 2021--2026 is held out.

\section{Method}
\emph{Models.} B0 and B1 are the base model prompted zero-shot and 3-shot. FT-B is LoRA on the full first-stage mix; FT-A is identical but without the generator slice (6,588 examples). FT-C continues training FT-B's adapter on a deep-learning stage: 600 verified DL problems, 307 DL concept Q\&A items over 36 syllabus topics (teacher-generated, MCQ/TF filtered by key agreement) and 1,200 replay examples sampled from the first-stage mix (2,107 examples, 0.61M tokens, 66 steps).

\emph{Training.} LoRA rank 16, $\alpha=32$, dropout 0.05 on q, k, v, o, gate, up and down projections (18.5M trainable parameters, 1.18\%); loss on assistant tokens only; AdamW, learning rate $2\times10^{-4}$ ($10^{-4}$ for FT-C) with cosine decay and 3\% warm-up; effective batch 32 (batch 1 $\times$ 32 accumulation); one epoch; bf16; length-grouped batches.

\emph{Hardware.} An Intel Core Ultra 5 125H with integrated Arc graphics (8.4\,GB shared memory). bitsandbytes 4-bit quantisation is not dependable on Intel XPU, so the base model is held in bf16 (the adapter is the same as in QLoRA). Batch 4 ran out of memory because the 152K-token vocabulary makes the logits alone about 2.5\,GB, hence gradient accumulation. One optimiser step takes about 62\,s; FT-B trained in 4.8\,h and FT-A in 3.7\,h.

\emph{Evaluation.} Adapters are merged and decoded greedily with the prompts used for the baselines: CS-Bench~\cite{csbench} (400 DSA/OS/CN multiple-choice and true/false items, accuracy), verified OS/CN/DBMS/DL test problems (100 each, exact match by a typed grader), MBPP (200, pass@1 with test execution), Spider dev (200, execution accuracy) and the held-out GATE CS questions (56). We report 95\% bootstrap confidence intervals and exact two-sided McNemar tests on paired items, and count unparseable answers separately so that learning the answer format is not mistaken for knowledge.

\subsection{RQ1: fine-tuning versus prompting}
FT-B significantly improves over the zero-shot base model on Spider (+9.5 points, $p=0.011$), DBMS functional-dependency problems (+15.0, $p=0.017$) and network numericals (+7.0, $p=0.039$) (Table~\ref{tab:results}, Fig.~\ref{fig:acc}). On CS-Bench the gain (+4.0) is not significant, and about half of it comes from fewer unparseable answers (21\ra 7 of 400); three-shot prompting remains slightly better on this knowledge-oriented benchmark. MBPP and GATE do not change significantly, so first-stage fine-tuning does not degrade code generation or examination performance. The only negative signal is CS-Bench's \emph{reasoning} subset, which fell by 6--7 points in both fine-tuned runs (not significant at $n=142$).

\subsection{RQ2: what the verified data contributes}
FT-A, trained on the same mix and settings minus the generator slice, stays at base-model level on every numerical task (CN 0\%; closure and candidate keys 0\% versus 32.8\% for FT-B). The numerical gains are therefore caused by the verified data rather than by teacher Q\&A, textbooks or examination questions. On CS-Bench, MBPP and GATE the two runs are within noise: the generated data is specific in its effect. FT-B also trains for 35\% more steps than FT-A, so part of any FT-B--FT-A difference could come from training length; a step-matched control is left to future work. CPU and disk scheduling stay at 0\% for every model: FT-B reproduces Gantt charts and tables perfectly but fills them with wrong values.

\subsection{RQ3: adding deep learning by continued training}
The deep-learning stage took 70\,min of training (66 steps). On the 100 held-out DL problems FT-C reaches 5.0\% exact match, against 3.0\% for FT-B and 2.0\% for the base model. Exact match is a harsh metric here because every number must be right (an output shape, a parameter count and a bias all at once). Measured per expected value, with the grader's tolerance, FT-C produces 26.0\% of the correct values, against 15.8\% for FT-B and 12.6\% for the base model (Table~\ref{tab:dl}); the improvement over FT-B is significant under a paired sign-flip permutation test ($p=0.013$; $p=0.001$ against the base model). Per problem type, value-level accuracy rises most for convolution shapes (22\ra 47\%), softmax/cross-entropy (0\ra 56\%) and classification metrics (22\ra 44\%), while one-step gradient descent (36\ra 8\%) and momentum (31\ra 19\%) get worse and attention weights and sigmoid backpropagation stay at 0\%. In the convolution problems FT-C applies the right formulas ($\lfloor (N+2P-K)/S \rfloor + 1$ and $(K\cdot K\cdot C+1)\cdot F$) but often slips on multi-digit products, the same procedural pattern as in Section~\ref{sec:errors}.

The stage did not erode earlier skills: against FT-B, DBMS (31.0 vs 30.0), CN (7.0 vs 8.0), Spider (59.5 vs 60.0) and MBPP (40.0 vs 42.5) all differ by at most a few items (McNemar $p\ge0.38$), and FT-C keeps its significant gains over the base model on DBMS ($p=0.003$) and Spider ($p=0.015$). Mixing 1,200 replay examples into a 2,107-example stage was enough to prevent forgetting at this scale.

\subsection{RQ4: explanation quality}
Final-answer accuracy does not measure explanations, and in the chat interface FT-C's concept answers were visibly shorter than the base model's. We therefore compare explanations directly on 39 held-out questions (19 verified numericals, one per problem type, with reference solutions, and 20 concept questions such as ``What is CNN?''). A fixed judge model (Gemma~4 31B) sees two answers with the model names hidden and scores correctness, steps and clarity (1--5); every pair is judged twice with the order swapped, and a model wins a question only if it wins in both orders. FT-C wins the numericals (14--4, sign test $p=0.031$) but loses the concept questions 6--13: its training targets were short (median 57--91 words for teacher answers), so it answers in 79 words where the base model uses 286. Two further continued-training stages address this. FT-D trains on 1,192 teacher answers written in a fixed teaching style (direct answer, numbered key points, a worked example, a one-line summary; plain-text math, no \LaTeX) with replay of verified problems; FT-E continues on fuller 250--350-word versions of the same answers (Table~\ref{tab:explain}).

FT-D keeps the numerical advantage and closes part of the explanation gap (concept steps 3.2 vs 2.7 for FT-C, clarity 3.9 vs 3.4), and its accuracy on deep-learning numericals rises from 5\% to 21\% (McNemar $p<0.001$ against FT-C), with no significant change on the other tasks. With fuller targets (median answer 194 words instead of 102), FT-E narrows the explanation gap on concept questions, but the base model is still slightly ahead (6--11--3, p = 0.332, not a significant difference): concept correctness 3.1 vs 3.3, steps 3.5 vs 4.0, clarity 3.8 vs 4.2 (out of 5). It still wins the numericals 13--5 (p = 0.096), and it is the most accurate model on DBMS (35\%, McNemar p = 0.001 vs the base model) while staying significantly ahead of the base model on DL (13\%), CN (11\%) and Spider (59.0\%), with code generation unchanged. Compared with FT-D it trades some DL accuracy (21 $\rightarrow$ 13) for DBMS (24 $\rightarrow$ 35).

\section{Error Analysis}\label{sec:errors}
We hand-labelled a stratified random sample of 50 wrong FT-B answers (12 CS-Bench, 8 each OS/CN/DBMS, 7 MBPP, 7 Spider) with one primary cause each (Table~\ref{tab:err}). None was a format failure.

\begin{table}[t]
\centering
\caption{Error categories of FT-B ($n=50$)}
\label{tab:err}
\begin{tabular}{@{}l r l@{}}
\toprule
Category & Share & Typical case \\
\midrule
Procedure / state tracking & 52\% & closure stops after one FD \\
Knowledge gap & 16\% & avoidance vs prevention \\
Schema hallucination & 12\% & column from wrong table \\
Arithmetic / units & 8\% & 0.96\,ms written as 9.6\,ms \\
Misread task & 6\% & number returned, bool expected \\
Answer contradicts reasoning & 4\% & argues A, answers B \\
Ambiguous item & 2\% & -- \\
\bottomrule
\end{tabular}
\end{table}

Procedure errors account for 20 of the 24 numerical failures and fall into three patterns: \emph{early stopping in fixed-point loops} (attribute closure applies one dependency and declares that nothing else applies), \emph{unfaithful reading of the input} (claiming an attribute never appears on a right-hand side when it does; ordering FCFS by process number instead of arrival) and \emph{inconsistent state} (LRU tables wider than the frame count; negative waiting times that are never checked). Arithmetic slips are a minority and are mostly powers of ten. Spider failures are grounding errors against a schema that is in the prompt. These patterns suggest concrete remedies: traces that restate the complete state at each step with built-in self-checks, tool use for arithmetic, and execution feedback for SQL.

\section{System}
The tutor is served by a small FastAPI application that loads the base model once and attaches the FT-A to FT-E adapters as named LoRA adapters, so the chat interface can switch between them, or disable them to show the base model, without reloading weights. Answers stream token by token with server-sent events; the browser interface renders Markdown, tables and highlighted code, writes any \LaTeX{} the model produces as plain readable text (e.g.\ ``z = $\Sigma$ w$_i$x$_i$ + b''), and keeps conversations locally. A second Gradio interface generates a fresh verified problem, lets the model solve it and grades the answer automatically. On the integrated GPU a typical answer streams in 20--30\,s.

\section{Limitations}
\begin{itemize}
\item One epoch per run and one seed per configuration; validation loss was still falling slowly (Fig.~\ref{fig:loss}).
\item FT-B trains for more steps than FT-A, which partly confounds the ablation.
\item The GATE test has only 56 items ($\pm$12-point intervals); MMLU was not evaluated.
\item Error labels come from a single annotator on a quota-stratified sample.
\item Explanation quality is judged by one LLM judge on 39 questions; a human rating would strengthen it.
\item FT-C was evaluated on five of the eight tasks (DL, DBMS, CN, Spider, MBPP) to save time; CS-Bench, OS and GATE were not re-run.
\end{itemize}

\section{Conclusion}
Verified, programmatically generated training data teaches a 1.5B model procedures that neither prompting nor LLM-written data teach: functional-dependency closure and keys, subnetting and CRC; a short continued-training stage with verified problems and replay adds measurable deep-learning skill (value-level 15.8\ra 26.0\%) without forgetting. The gains are specific and do not cost code-generation ability. Training on fuller teaching-style answers narrows, but does not close, the gap to the base model's explanations of open concept questions while keeping the accuracy advantage. The main limitation is execution of long procedures, which the model imitates rather than performs. Future work: more epochs and self-checking traces, tool use for arithmetic and simulation, preference tuning on verified correct/incorrect pairs, and a step-matched ablation.
