CSE-Tutor: Teaching a Small Language Model to Solve and Explain Computer Science Problems

Satya Dedeepya
Course project, Deep Learning · github.com/satyadedeepya/slm_dl_project

Abstract—Small language models can run on a student's own laptop, for free and without sending data anywhere. However, they often get the numerical problems of computer-science exams wrong. We fine-tuned Qwen2.5-1.5B-Instruct with LoRA to work as a tutor for six subjects: data structures, programming, databases (DBMS), operating systems (OS), computer networks (CN) and deep learning (DL). The key idea is verified training data: we wrote 41 small programs that create practice problems and compute the correct answer by running the real algorithm, so every answer is guaranteed to be right. All training and testing ran on a laptop with an integrated Intel GPU. On unseen test questions, the fine-tuned model is clearly more accurate than the original model: SQL writing rises from 50.5% to 60.0%, DBMS problems from 15% to 30% and networking problems from 1% to 8%, and an experiment without the verified data shows that this data causes the gains. We then added deep learning and two training stages that teach the model to explain like a teacher. A blind comparison by a judge model shows that the final model solves numerical problems better than the original model (13 wins to 5) and is much more accurate (DBMS 15→35%, DL 2→13%), while the original model still explains open concept questions slightly better.

Index Terms—small language models, fine-tuning, LoRA, synthetic data, computer science education.

I. Introduction

Students preparing for university exams, GATE and job interviews need a helper that can explain ideas, solve numerical problems step by step and write correct code and SQL. Large online models such as ChatGPT can do this, but they need the internet, may cost money and send the student's data to a company. A small model with 1.5 billion parameters can run on an ordinary laptop instead. The problem is that, out of the box, such a model gets many exam problems wrong. For example, it copies the shape of a CPU-scheduling solution but fills it with wrong waiting times.

The usual way to improve a small model is to fine-tune it on questions and answers written by a bigger model [9], [10]. But those answers are not checked, so the small model can learn the big model's mistakes. We take a different approach for the parts of the syllabus that are calculations. We write generators: short programs that make a random problem and then compute its answer by actually running the algorithm (for example, simulating the CPU scheduler or the CRC division). Every training answer they produce is correct by construction.

We study four questions:

  • RQ1: How much does fine-tuning improve a small model compared with simply prompting it?
  • RQ2: Is the verified data really the reason for the improvement on numerical problems?
  • RQ3: Can we add a new subject (deep learning) later without the model forgetting what it learned?
  • RQ4: Does the fine-tuned model also explain better than the original model, and if not, can we fix that?

Our main contributions are: (1) 41 tested problem generators for OS, CN, DBMS and DL; (2) a controlled experiment showing that the verified data causes the gains; (3) careful testing on seven unseen test sets with statistical tests; (4) a blind, fair way to compare explanations, and two training stages that improve them; and (5) a chat app that runs fully on a laptop.

II. Related Work

LoRA [1] fine-tunes a model by training small extra matrices instead of all its weights, and QLoRA [2] also compresses the base model to 4 bits. We use LoRA on Qwen2.5-1.5B-Instruct [3]. Other work has fine-tuned models for programming education [5], for data-structures problems [6] and as local teaching assistants [7], [8]. CS-Bench [4] is a benchmark for computer-science knowledge, and we use it in our tests. Self-Instruct [9] and GLAN [10] build training data with language models, and Orca [11] shows that small models learn a reasoning style by copying a teacher's step-by-step explanations. LIMA [12] argues that fine-tuning mainly teaches the format of answers, which matches what we found. Strong models can act as judges of answer quality, but they tend to prefer the first or the longer answer [13], so we judge each pair twice in swapped order. Training on a new task can make a model forget old skills [14]; we reduce this by mixing old examples into every new stage.

III. Methodology

Fig. 1 gives an overview. We collect training data from four kinds of sources, each with its own quality check, train five versions of the model one after another, test each version, and serve all of them in one chat app.

A. Verified problem generators

Each generator picks random numbers, runs the real algorithm and writes a step-by-step solution that ends with a line “Final answer: …”. It also stores the answer in a form a program can check automatically (Table I). Questions state any rules that could change the answer, such as how ties are broken. Test problems use different number ranges from training problems, so the model cannot memorise them. We checked the generators with automatic tests: against worked examples from standard textbooks, and, for deep learning, by computing the same answers again with PyTorch.

B. The training data

The main training set has 9,335 examples (Table II). Besides 2,400 generated problems, it contains GATE and ISRO past exam questions, short concept questions and answers, questions based on free textbooks, SQL questions from Spider [15] and Python tasks from MBPP [16] and CodeAlpaca. Where a bigger “teacher” model wrote explanations, it did so without seeing the official answer, and we kept an explanation only if the teacher's answer matched the official key (990 of 1,154 GATE/ISRO questions). We removed duplicate examples and any training example that overlapped with a test question.

C. Five training stages

We used LoRA with rank 16, which trains only 18.5 million of the 1.5 billion parameters (1.18%). Each stage ran for one pass over its data (one epoch) with an effective batch of 32 examples. The laptop's integrated Intel GPU does not support 4-bit models reliably, so we kept the base model in 16-bit precision. Table III lists the five stages:

  • FT-A and FT-B are a matched pair. FT-B uses the full training set; FT-A uses the same set without the generated problems. Comparing them shows what the verified data adds.
  • FT-C continues from FT-B and adds deep learning: 600 verified DL problems and 307 DL concept answers. It also includes 1,200 old examples (“replay”) so the model does not forget earlier subjects.
  • FT-D and FT-E teach the explanation style. We noticed that the teacher's concept answers in the training data were short (median 57–91 words), while the original model writes about 290 words. So we wrote new answers for about 1,300 concept questions in a fixed teaching format: a direct answer, numbered key points, a worked example and an “In short” summary, with all maths written as plain text. FT-D learns these answers (median 164 words); FT-E learns fuller versions of 250–350 words. Both also replay verified problems to keep the accuracy.

D. How we tested the models

Accuracy. We tested every model on questions it had never seen: 400 CS-Bench questions [4], 100 new generated problems each for OS, CN, DBMS and DL, 200 MBPP coding tasks (the code must pass its tests), 200 Spider SQL questions (the query must return the right result) and 56 recent GATE questions. We compared the fine-tuned models with the original model, both without examples (B0) and with three worked examples in the prompt (B1). To check whether a difference is real or just luck, we used the McNemar test [17], which compares two models on the same questions; a difference with p < 0.05 is called significant.

Explanation quality. Accuracy only checks the final answer, not whether the explanation helps a student. So we also ran a blind comparison on 39 unseen questions: 19 numerical problems (with their correct solutions) and 20 concept questions such as “What is CNN?”. A separate judge model (Gemma 4 31B) sees two answers labelled only “A” and “B”, scores each for correctness, steps and clarity from 1 to 5, and picks the better one. It is told not to prefer an answer just because it is longer. Each pair is judged twice with A and B swapped, and a model wins a question only if it wins both times.

E. The chat app

To make the tutor usable, we built a chat app that runs on the same laptop. A small Python server loads the original model once and attaches all five trained versions as separate LoRA adapters, so the user can switch between them, or switch them off to see the original model, without reloading anything. Answers appear word by word. Any mathematics the model writes in LaTeX code is shown as plain readable text, for example “z = Σ wixi + b”, so students never see raw symbols. A second app creates a fresh generated problem, lets the model solve it and marks the answer right or wrong using the computed solution.

A. RQ1: Does fine-tuning help?

Yes, on the tasks where we had strong data (Table V and Fig. 2). FT-B is significantly better than the original model at writing SQL (50.5→60.0%), at DBMS problems (15→30%) and at networking problems (1→8%). Coding (MBPP) and GATE scores did not change, so the model did not lose general skills. On CS-Bench, which tests broad knowledge, fine-tuning helped only a little (+4 points), and about half of that came from the model writing its answer in the expected format more often. Here, simply giving the original model three examples (B1) worked slightly better. OS problems stayed hard for every model.

B. RQ2: Is the verified data the reason?

Yes. FT-A was trained in exactly the same way as FT-B but without the generated problems, and it stayed at the original model's level on every numerical test (for example 0% on networking problems, while FT-B reached 8%; p = 0.008). On the other tests the two models are about equal. So the verified data is what teaches the procedures, such as finding attribute closures and subnet ranges. One caution: FT-B also trained for 35% more steps than FT-A.

C. RQ3: Adding deep learning without forgetting

FT-C learned deep learning in 70 minutes of extra training. Getting every number of a DL answer right is hard, so we also measured the share of correct numbers in each answer: it rose from 15.8% (FT-B) to 26.0% (FT-C), a significant gain. The biggest improvements were in convolution sizes (22→47%) and softmax loss (0→56%). Thanks to the replayed old examples, the scores on DBMS, networking, SQL and coding stayed the same. The later stages FT-D and FT-E improved DL further, to 21% and 13% fully correct answers.

D. RQ4: Does the model explain well?

Table VI shows the blind comparison against the original model. FT-C solved numerical problems better (14 wins to 4) but lost on concept questions (6 to 13). Its answers were short, a median of 79 words against 286 for the original model, because it had learned from short training answers. The judge gave FT-C 2.7 out of 5 for explaining the steps of concept answers, against 4.2 for the original model.

The teaching-style stages fixed part of this problem. FT-D and FT-E kept the lead on numerical problems, and FT-E's answers became much fuller (194 words). Its score for explaining concept steps rose to 3.6 (original: 4.0). However, the original model still won slightly more concept questions (11 to 6, with 3 ties); this difference is not significant. FT-E is also the most accurate model on DBMS problems (35%) and is significantly better than the original model on DBMS, DL, networking and SQL, with coding unchanged.

The judge's comments show why the fine-tuned model wins numerical questions. On the convolution problem from Section III-A, both models gave a wrong final number. The original model used the wrong formula, ignoring the padding. FT-E used the correct formula and the correct values, but made one subtraction mistake:

FT-E's answer (shortened)
Output size = (N + 2P − K) / S + 1
            = (227 + 2·5 − 11) / 2 + 1 = 219 / 2 + 1 = 110
Parameters  = (11·11·6 + 1) × 20 = 14740

(227 + 10 − 11 is 226, which gives 114 and 14,540.) The judge preferred FT-E because it “uses the correct formulas and fails only on basic arithmetic.”

E. Where the model still makes mistakes

To understand the remaining errors, we read 50 wrong answers of FT-B by hand and gave each one main cause (Table VIII). None of them failed because of the answer format: the model fully learned how to present a solution. More than half were errors in carrying out a long procedure. For example, when finding an attribute closure, the model applied one dependency and then stopped too early; in FCFS scheduling it ordered processes by their number instead of their arrival time; in LRU page replacement it drew a table with more frames than allowed. The model knows the method, but it does not track every step reliably. SQL errors were mostly about using a column from the wrong table, even though the table definitions were given.

V. What We Learned

Checked answers beat more answers. The generated problems were only about a quarter of the training data, yet they were the only part that improved numerical accuracy. Teacher-written answers, textbook questions and exam questions did not have this effect. For calculation-heavy topics, a few thousand correct worked solutions are worth more than many unchecked ones.

The model copies the style of its training answers. When the training answers were short, the model's answers became short, even for open questions where the original model gave long, clear explanations. When we trained on longer teaching-style answers, the model's answers grew from 79 to 194 words and followed the same structure. This means that good explanations have to be designed into the training data; they do not appear by themselves.

Accuracy and explanation are different goals. A model can become more accurate while explaining less, as FT-C did. Measuring only accuracy would have hidden this. The blind comparison made it visible and showed whether each fix helped.

Each stage has trade-offs. FT-D is best on deep-learning problems, while FT-E is best on DBMS problems and gives fuller explanations. Because each stage was trained only once, part of these differences may be due to chance, so the chat app keeps both versions available.

A laptop is enough. All five training stages together took about 12.6 hours on an integrated GPU. The main practical problems were memory limits, missing 4-bit support and the laptop going to sleep during long runs, which we solved with gradient accumulation, saved checkpoints and a keep-awake setting.

VI. Conclusion

We showed that a small 1.5-billion-parameter model, fine-tuned on a laptop, can become a much better computer-science tutor. The most important ingredient is training data whose answers are computed by code: it taught the model procedures that neither prompting nor AI-written answers taught, and a controlled experiment confirmed this. New subjects can be added in about an hour of extra training without forgetting old ones. We also found that the model copies the length and style of its training answers. Short answers made it accurate but terse, and longer teaching-style answers brought its explanations close to, but not yet above, the original model's.

Limitations. Our study has some limits that readers should keep in mind:

  • Each stage was trained only once and for one epoch, so some differences between stages may be due to chance.
  • FT-B trained for more steps than FT-A, which slightly weakens the comparison between them.
  • The explanation test uses one AI judge and only 39 questions; a rating by human teachers would make it stronger.
  • The GATE test has only 56 questions, and the later models were tested on five of the eight test sets to save time.
  • Some training answers were written by a larger AI model, which can make mistakes even after our checks.

Future work. We see four clear next steps: let the model call a calculator or run code for arithmetic and long simulations [19]; train for more epochs with several random seeds; use preference training such as DPO [18] on the answer pairs the judge already compared; and test the tutor with real students in a course.

Responsible use. Because the tutor runs on the student's own laptop, no data leaves the device. Its answers can still be wrong, especially in long calculations, so the app says this clearly and the practice mode always shows the verified answer.
