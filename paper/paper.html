CSE-Tutor: Verified Synthetic Data for Fine-Tuning a 1.5B-Parameter Tutor Model for Computer Science Education

Satya Dedeepya
Course project, Deep Learning · github.com/satyadedeepya/slm_dl_project

Abstract—Small language models can run on a student's laptop, but they are unreliable on the numerical problems that dominate computer-science examinations. We fine-tune Qwen2.5-1.5B-Instruct with LoRA as a tutor for six subjects (data structures and algorithms, programming, databases, operating systems, computer networks and deep learning) using a mixed instruction set whose distinctive component is programmatically verified data: 3,000 problems whose step-by-step solutions and answers are computed by executing the underlying algorithm. All training and evaluation runs on an integrated Intel Arc GPU. On held-out test sets, fine-tuning significantly improves text-to-SQL execution accuracy (50.5→60.0), functional-dependency problems (15→30) and network numericals (1→8) over the base model (exact McNemar p < 0.05), without loss on code generation. An ablation that removes only the verified data eliminates these numerical gains. A continued-training stage adds deep learning, DL_ABSTRACT. Error analysis shows that the remaining failures are mostly procedural: the model reproduces the solution template but executes multi-step algorithms unreliably.

Index Terms—small language models, LoRA, synthetic data, data verification, computer science education, text-to-SQL.

I. Introduction

Students preparing for university examinations, GATE and placement interviews need an assistant that explains concepts, solves numerical problems step by step and writes correct code and SQL. Large hosted models do this well but cost money and need connectivity; a 1.5B-parameter model runs locally, but out of the box it computes CPU-scheduling waiting times, page faults and subnet ranges incorrectly because it pattern-matches instead of executing the procedure.

The common recipe for adapting a small model is to fine-tune on question–answer pairs written by a larger model [11], [12]. Such labels are unverified, and a small student model can learn the teacher's mistakes. We take a different route for the part of the curriculum that is algorithmic: we write generators that sample random problem instances and compute their solutions by running the algorithm, so every label is correct by construction. We then ask three questions:

  • RQ1: how much does LoRA fine-tuning improve a 1.5B model on CS tasks compared with zero- and few-shot prompting?
  • RQ2: does the verified numerical data cause the improvement on numerical problems, or does the rest of the mix?
  • RQ3: can a new subject (deep learning) be added cheaply by continued training without forgetting earlier skills?

Our contributions are (1) verified generators for 41 problem types across operating systems, networks, databases and deep learning, with tests against textbook examples and PyTorch; (2) a controlled ablation isolating the effect of verified data; (3) a statistically careful evaluation (bootstrap confidence intervals, exact McNemar tests, separated format failures) on seven held-out benchmarks; (4) an error taxonomy of the fine-tuned model; and (5) a local chat interface. The whole pipeline runs on a laptop with an integrated GPU.

II. Related Work

Parameter-efficient fine-tuning. LoRA [1] trains low-rank updates of frozen weights; QLoRA [2] adds 4-bit quantisation of the base model. We use LoRA on all attention and MLP projections of Qwen2.5-1.5B-Instruct [3], [4].

Models for CS education. GuideLM [6] shows that small supervised sets can shape pedagogical behaviour; QLoRA has been applied to DSA problems [7]; local open-source teaching assistants are studied in [8]–[10]. CS-Bench [5] is the closest benchmark and serves as our multiple-choice evaluation.

Synthetic instruction data. Self-Instruct [11] and GLAN [12] generate instruction data with language models. Our generators are programs, so correctness does not depend on a teacher model; LLM-written data in our mix is filtered by answer-key agreement instead.

Forgetting. Parameter-efficient tuning still forgets [13]; we therefore keep replay data and measure code generation and examination questions after every stage.

III. Data

A. Verified generators

Each generator samples parameters, runs the algorithm and writes a solution in a fixed teaching format that ends with a Final answer: line, plus a machine-readable grading specification (Table I). Questions state their conventions (tie-breaking, whether C-SCAN counts the return seek) so the reference answer is unambiguous. Test problems are drawn from parameter pools disjoint from training. Correctness is checked by unit tests against textbook worked examples (e.g. Silberschatz scheduling and page-replacement figures), property tests (Belady's optimality, safety-sequence validity), and, for deep learning, by recomputing answers with PyTorch layers and autograd.

B. The full training mix

The first-stage mix (9,335 examples, 2.68M tokens; Table II) combines the generators with GATE/ISRO previous-year questions whose explanations were produced by a teacher model without the key and kept only when the teacher agreed with the official answer (990 of 1,154), concept Q&A over a 133-topic syllabus, Q&A grounded in four openly licensed textbooks, Spider [14] text-to-SQL with real schemas, MBPP [15] and CodeAlpaca for code, and general replay data. All sources are deduplicated with MinHash and decontaminated against every evaluation set with 13-gram overlap. GATE papers up to 2020 and half of 2021–2026 are used for training; the other half of 2021–2026 is held out.

IV. Method

Models. B0 and B1 are the base model prompted zero-shot and 3-shot. FT-B is LoRA on the full first-stage mix; FT-A is identical but without the generator slice (6,588 examples). FT-C continues training FT-B's adapter on a deep-learning stage: DL_STAGE_MIX.

Training. LoRA rank 16, α = 32, dropout 0.05 on q, k, v, o, gate, up and down projections (18.5M trainable parameters, 1.18%); loss on assistant tokens only; AdamW, learning rate 2×10−4 (10−4 for FT-C) with cosine decay and 3% warm-up; effective batch 32 (batch 1 × 32 accumulation); one epoch; bf16; length-grouped batches.

Hardware. An Intel Core Ultra 5 125H with integrated Arc graphics (8.4 GB shared memory). bitsandbytes 4-bit quantisation is not dependable on Intel XPU, so the base model is held in bf16 (the adapter is the same as in QLoRA). Batch 4 ran out of memory because the 152K-token vocabulary makes the logits alone about 2.5 GB, hence gradient accumulation. One optimiser step takes about 62 s; FT-B trained in 4.8 h and FT-A in 3.7 h.

Evaluation. Adapters are merged and decoded greedily with the prompts used for the baselines: CS-Bench [5] (400 DSA/OS/CN multiple-choice and true/false items, accuracy), verified OS/CN/DBMS/DL test problems (100 each, exact match by a typed grader), MBPP (200, pass@1 with test execution), Spider dev (200, execution accuracy) and the held-out GATE CS questions (56). We report 95% bootstrap confidence intervals and exact two-sided McNemar tests on paired items, and count unparseable answers separately so that learning the answer format is not mistaken for knowledge.

A. RQ1: fine-tuning versus prompting

FT-B significantly improves over the zero-shot base model on Spider (+9.5 points, p = 0.011), DBMS functional-dependency problems (+15.0, p = 0.017) and network numericals (+7.0, p = 0.039). On CS-Bench the gain (+4.0) is not significant, and about half of it comes from fewer unparseable answers (21→7 of 400); three-shot prompting remains slightly better on this knowledge-oriented benchmark. MBPP and GATE do not change significantly, so first-stage fine-tuning does not degrade code generation or examination performance. The only negative signal is CS-Bench's reasoning subset, which fell by 6–7 points in both fine-tuned runs (not significant at n = 142).

B. RQ2: what the verified data contributes

FT-A, trained on the same mix and settings minus the generator slice, stays at base-model level on every numerical task (CN 0%; closure and candidate keys 0% versus 32.8% for FT-B). The numerical gains are therefore caused by the verified data rather than by teacher Q&A, textbooks or examination questions. On CS-Bench, MBPP and GATE the two runs are within noise: the generated data is specific in its effect. FT-B also trains for 35% more steps than FT-A, so part of any FT-B–FT-A difference could come from training length; a step-matched control is left to future work. CPU and disk scheduling stay at 0% for every model: FT-B reproduces Gantt charts and tables perfectly but fills them with wrong values.

VI. Error Analysis

We hand-labelled a stratified random sample of 50 wrong FT-B answers (12 CS-Bench, 8 each OS/CN/DBMS, 7 MBPP, 7 Spider) with one primary cause each (Table IV). None was a format failure.

Table IV

Procedure errors account for 20 of the 24 numerical failures and fall into three patterns: early stopping in fixed-point loops (attribute closure applies one dependency and declares that nothing else applies), unfaithful reading of the input (claiming an attribute never appears on a right-hand side when it does; ordering FCFS by process number instead of arrival) and inconsistent state (LRU tables wider than the frame count; negative waiting times that are never checked). Arithmetic slips are a minority and are mostly powers of ten. Spider failures are grounding errors against a schema that is in the prompt. These patterns suggest concrete remedies: traces that restate the complete state at each step with built-in self-checks, tool use for arithmetic, and execution feedback for SQL.

VII. System

The tutor is served by a small FastAPI application that loads the base model once and attaches the FT-A, FT-B and FT-C adapters as named LoRA adapters, so the chat interface can switch between them, or disable them to show the base model, without reloading weights. Answers stream token by token with server-sent events; the browser interface renders Markdown, tables and highlighted code and keeps conversations locally. A second Gradio interface generates a fresh verified problem, lets the model solve it and grades the answer automatically. On the integrated GPU a typical answer streams in 20–30 s.

VIII. Limitations

  • One epoch per run and one seed per configuration; validation loss was still falling slowly.
  • FT-B trains for more steps than FT-A, which partly confounds the ablation.
  • The GATE test has only 56 items (±12-point intervals); MMLU was not evaluated.
  • Error labels come from a single annotator on a quota-stratified sample.
  • DL_LIMIT

IX. Conclusion

Verified, programmatically generated training data teaches a 1.5B model procedures that neither prompting nor LLM-written data teach: functional-dependency closure and keys, subnetting and CRC, and DL_CONCL. The gains are specific and do not cost code-generation ability. The main limitation is execution of long procedures, which the model imitates rather than performs. Future work: more epochs and self-checking traces, tool use for arithmetic and simulation, preference tuning on verified correct/incorrect pairs, and a step-matched ablation.
